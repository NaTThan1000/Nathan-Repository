### 1.4 AI Git 写入操作权限边界 [2026-07-20]

**核心原则：AI 绝不得在用户未明确要求时自动执行任何 Git 写入操作。**

受限制的操作（禁止自动执行）：
- `git commit` — 创建提交
- `git push` — 推送到远程
- `git merge` — 合并分支
- `git rebase` — 变基操作
- `git reset --hard` / `git checkout --` 等破坏性操作
- 任何会修改 Git 历史或远程仓库的操作

允许的操作（无需用户确认）：
- `git status` — 查看状态
- `git diff` — 查看差异
- `git log` — 查看历史
- `git branch` — 查看分支
- 其他纯读取操作

**触发条件**：只有当用户当前消息中包含以下任一明确指令时，AI 才能执行 Git 写入操作：
- "提交" / "commit"
- "推送" / "push"
- "合并" / "merge"
- "同步文档"（该指令隐含后续的 commit+push+merge 流程）

**禁止行为**：AI 完成代码修改任务后，将修改保留在工作树中即可，不得自动追加 commit/push/merge 等"收尾"操作。用户会自行决定何时提交。

## 2. 文档体系规范

### 2.1 三层记忆结构 [2026-07-20]

| 层级 | 文件 | 定位 | 更新时机 |
|------|------|------|---------|
| L1 | `Documents/global-rules.md` | 跨项目通用规范 | 用户要求同步文档时 |
| L2 | `{project}/Documents/{project}-memory.md` | 单个项目决策记忆 | 用户要求同步文档时 |
| L3 | `{project}/Documents/{project}-context.md` | 策划文档 + 技术速查 | 用户要求同步文档时 |

**注意**：三层文档的更新时机与合并 main 分支是两个独立操作。用户大多数情况下会同时说"同步文档 + 合并 main"，但理论上两者解耦——可能只同步文档不合并 main，也可能只合并 main 不同步文档。

### 2.2 上下文文档同步规则 [2026-07-16, 2026-07-20修正, 2026-07-28修正, 2026-07-31强化]

- 同步时机：由用户主动触发（说"同步文档"或类似指令），与合并 main 分支独立
- 日常开发修改时不需要同步，等用户认为一个阶段完成时再要求同步
- **AI 不得在代码修改任务中附带更新任何项目文档**。文档更新仅在用户发出"同步文档"指令时执行。此规则优先级高于 AI 对"代码和文档应保持一致"的默认行为倾向，旨在尊重用户的工作节奏（代码改动高频实验性、文档更新低频确认性）
- **【强制步骤 0】同步开始前，必须回溯本轮会话中所有"发现但未修"的代码-文档不一致，逐条列出完整清单，逐一确认是否已修正。** 来源包括但不限于：用户口头指出但未当场修的、代码比对中发现的、对话中"顺便提一下"的事项。本次回溯列为第一优先级，必须在任何其他同步操作之前完成。此步骤旨在根除"改A→改B→同步时只修B"的系统性遗漏缺陷
- 同步时必须进行全覆盖检查，不能只更新与当天修改相关的几个点：
  - 操作键/按键表
  - 核心属性/玩家属性
  - 渲染常量（确认值是当前实际值）
  - 架构概览（确认新增系统模块已加入）
  - TILE系统/楼层系统等核心系统描述
  - 章节编号（无重复无遗漏）
  - 函数索引（补充所有新增函数）
  - 数据流（补充启动/探索/楼层等完整流程）
  - 游戏流程（补充探索模式+战斗模式完整流程）
  - UI面板（补充楼层信息栏等新增UI）
  - 文件清单（补充新配置文件）
  - 下一步方向（移除已完成的）
  - 过期内容清理（已淘汰的描述）

### 2.3 同步文档 + 合并 main 完整流程 [2026-07-16 优化, 2026-07-20 解耦]

> **说明**：以下描述的是用户同时要求"同步项目文档，提交并推送，并合并到main分支"时的完整操作流程。**同步文档**和**合并 main** 本质上是两个独立操作，此处放在一起描述仅因为用户通常同时要求两者。

当用户同时要求同步文档和合并 main 时：

1. **同步文档**：先更新三份文档（global-rules.md / memory.md / context.md 中涉及的部分），在"最近更新记录"顶部新增一条
2. **全面检查变更**：`git status` + `git diff` 仔细检查所有变更文件
3. **一次性提交**：所有相关变更（代码 + 文档）纳入同一个 commit
4. **推送到远程**：push 当前分支到 origin
5. **合并到 main**：切到 main → pull → merge 当前分支 → push main
6. **切回开发分支**：回到当前功能分支

**关键优化**：先更新文档再提交，避免之前"先提交代码 → 合并main → 再提交文档 → 再合并main"的重复操作。

### 2.4 多端开发记忆同步 [2026-07-20]

- **切换电脑前**：`commit + push` 当前分支（即使不合并 main），确保三份记忆文件已更新
- **切换电脑后**：`pull` 最新，然后主动告知 AI 读取三份文档
- **新会话启动**：主动提示 AI 读取 `global-rules.md` + 当前项目的 `{project}-memory.md` + `{project}-context.md`

### 2.5 global-rules 修改规则 [2026-07-20, 2026-08-06扩充]

- **用户要求时先分析再写入**：用户说"写到 global-rules 里""加到规则里"等指令时，AI 必须先审查该内容：是否与现有规则冲突、逻辑是否自洽、是否有实际规范价值。审查结果向用户汇报（无问题则简述确认，有问题则列出具体冲突/疑问），用户最终确认后再写入。不得无脑直接写入，也不得推脱让用户自己手动加
- **AI 主动发现时同步确认**：AI 在对话中判断某个行为模式或规范需要写入 global-rules 时（如反复出现的问题、需要标准化的工作流、新确立的约定等），必须主动向用户提出："我发现 X 这个模式/规范可能需要写入 global-rules，你觉得需要加吗？" 用户确认后再写入。AI 不得在用户未表态的情况下自行新增规则条目
- **可以修改已有规定**：随着开发习惯演变，可以更新旧的规范条目
- **冲突必须询问**：如果新规范与旧规范冲突，AI 必须先向用户明确指出冲突内容，询问保留哪种规范，得到确认后才能修改
- **唯一性要求**：global-rules 内部不能有自相矛盾的内容，每一条规范必须是唯一且无歧义的
- **时间标注**：修改已有条目时，在标题日期字段追加新日期，如 `[2026-07-16, 2026-07-20修正]`

### 2.6 memory 修改规则 [2026-07-20]

- **不可修改或删除已有记录**：一旦写入的历史内容永久保留
- **新方案追加方式**：当方案从 A 改为 B 时，不能只保留 B 删除 A。必须在对应章节顶部追加 B 的记录并标注"[当前方案]"，A 的原记录保留并标注"[已废弃]"
- **反复变更完整保留**：即使出现 X→Y→X 的反复，每一步都要保留，形成完整的演变时间线
- **当前结论标注**：每个主题下必须有明确的当前结论标注（"[当前方案]"），让读者一眼看到最终状态

### 2.7 一致性原则 [2026-07-20]

| 文档 | 是否允许冲突 | 说明 |
|------|:--:|------|
| `global-rules.md` | ❌ 不允许 | 必须是唯一、无歧义的规范。新旧冲突时必须询问用户选择。 |
| CodeBuddy Memories | ❌ 不允许 | 与 global-rules.md 保持一致，两者可互相校验。 |
| `{project}-memory.md` | ✅ 允许 | 可记录冲突的决策过程（A→B→A），但必须有明确的"[当前方案]"标注。 |

### 2.8 文档写入前验证流程 [2026-07-21]

**核心原则：在对任何文档（memory.md、context.md 等）进行追加写入前，必须先完成排序验证。**

每次追加前触发以下检查：
1. **先读取全文**：确认当前最后一个已记录条目是什么日期、什么内容
2. **确认追加位置**：新条目追加在文件末尾（或同日期段落末尾），不得插入到已有条目之间
3. **同一天多个条目**：按实际对话先后顺序从上到下排列，不在条目标题中使用分钟级时间标注
4. **写入后复核**：如果涉及条目移动或重组，写入后重新读取全文确认排序正确

此规范适用于所有项目的 memory.md 和 context.md 文件。

### 2.9 规则传播检查 [2026-07-21]

**核心原则：当用户发出"同步项目文档 + 提交推送 + 合并 main"指令时，在同步三份文档的过程中，必须检查本期项目级文档（memory.md / context.md）中的新增规则是否跨项目通用，是则同步到 `global-rules.md`。**

触发时机精确绑定在用户的同步指令上，不在日常开发的每次文档修改时触发。这样做的好处：
- 同步文档本身就是一个系统性审查节点，在此处追加规则传播检查最自然、最少遗漏
- 日常开发中文档修改频繁，每次都触发反而导致麻木，不如集中在审查节点一次性处理

检查标准：
- 本期在 memory.md / context.md 中新增或修改了哪些规则/规范？
- 这些规则是否跨项目通用？（match3-rpg、tarot-battle、Project-Issac-turnbase 都适用？）
- 如果是 → 必须同步写入 `global-rules.md` 对应章节
- 如果仅适用当前项目 → 留在项目级文档即可

此检查应在 §2.3 流程的"同步文档"步骤中优先执行，与其他文档更新一同纳入 commit。

### 2.10 Memory 记录完整性要求 [2026-07-23, 2026-07-24更新×2]

**核心原则：memory.md 的本质是对话记忆，不是代码变更日志。写入时不得遗漏任何可能在将来对话中需要回溯的讨论内容，无论该讨论是否涉及代码变更。**

具体要求：
- **不只记结果**：除了最终的代码或配置变更，还要记录"为什么这样做"的推理链、被否决的替代方案、确立的分类标准等
- **想法推进的完整轨迹**：记录一个想法从 A→B→C 的演变全过程，包括每次转变的原因和触发条件。不跳步骤、不只保留最终态。例如"方案从 A 改为 B 因性能问题，后又从 B 改为 C 因用户体验不佳"，每一步都要有
- **AI 建议的采纳状态**：当用户发起方向性讨论（如"下一步该做什么"），AI 给出的每条建议需要标注用户反馈状态——采纳（并后续执行了）、否定（并说明原因）、无视（未回应）。这确保了将来回溯时能知道"当时 AI 提过哪些方案、哪些走了哪些没走、为什么"
- **审计/审查类讨论**：如果当天进行了系统性审计（如配置审查、代码检查），必须记录审计范围、分类标准、审计结论（哪类改/哪类不改/各自原因）
- **策略/流程类讨论**：如果当天确立了新的同步策略、维护流程、验证方法，必须完整记录
- **设计验证/待办任务**：如果 AI 给用户列出了验证清单、待验证设计假设、需要用户亲自体验的测试项等，必须记录。这些是"后续需要跟进的工作方向"，在将来对话中可能需要回溯
- **零遗漏检查**：写入 memory 前必须回溯当天完整对话，逐条确认是否有未被记录的决策或讨论内容

**记忆触发标准**：如果一段对话内容在下次切换电脑后、新会话中可能需要被回溯引用 → 必须记录到 memory。这包括但不限于：
- 代码/配置变更及其推理链
- 设计原则、方法论、分类标准的讨论
- 验证清单、待办测试项、设计疑问
- 待定方案、创意方向、未决事项
- 流程/策略决策
- AI 建议列表及其采纳/否定/无视状态
- 想法演变轨迹（A→B→C 全过程及每次转变原因）

此规范适用于所有项目的 memory.md 文件。

### 2.11 代码-文档不一致处理约定 [2026-07-28]

**核心原则：当 AI 发现实际代码和项目文档（context.md / memory.md）不一致时，必须主动提醒用户，列出具体差异清单，让用户决策如何处理。不得在用户未表态的情况下擅自修改代码或擅自修改文档。**

处理选项：
1. **以代码为准更新文档**：代码是事实，文档过期 → 修改文档匹配代码
2. **以文档为准修正代码**：文档是设计意图，代码实现出错 → 修改代码匹配文档
3. **两者都保留**：设计变更过渡期，暂时允许不一致 → 标记为 [过渡期] 待后续统一

注意事项：
- 此约定适用于任何状态下发现不一致的情况（日常开发、同步文档、代码审查等），不限于"同步文档"指令期间
- 在用户明确要求"同步文档"时，默认采用选项①（以代码为准更新文档），但仍应在更新前列出差分供用户审视
- 用户会尽量告知手动修改的内容，减少信息不对称
- 此规则覆盖所有有副作用的修正操作（文件写入、代码修改等）

### 3.4 JSON 文件编辑后校验规范 [2026-07-31]

- **优先策略**：对于涉及多条目增删的复杂 JSON 修改，优先使用"读取整个文件 → 逻辑层修改 → `write_to_file` 整体写回"的方式，写回前完整解析验证合法性，避免局部替换带来的逗号遗漏
- 此规范适用于所有项目中的所有 JSON 配置文件

## 4. AI 会话规范

### 4.1 新会话启动约定 [2026-07-20, 2026-07-31修正]

- AI 会自动加载 CodeBuddy Memories 中的精简规则
- AI 在新会话时必须**主动**读取 `global-rules.md` — 用户已在 CodeBuddy 设置中配置系统级规则"每次对话自动读取 global-rules.md"，AI 不得等待用户指令，应在会话第一条消息处理前完成此读取
- 用户主动告诉 AI 读取项目级文档（memory.md + context.md）
- 三文件通过 Git 多端同步，保证不同电脑间记忆一致

### 4.1.1 Skill 使用规范 [2026-08-06]

**核心原则：当系统中有对应的 skill 可用时，必须通过 `use_skill` 工具加载 skill 来执行任务，不得手动模拟 skill 的工作流程。**

可用 skill 及触发场景：

| Skill 名称 | 触发场景 |
|-----------|---------|
| `daily-start` | 用户发出 `daily start`、`加载项目记忆`、`读取项目文档`、`开始今天的工作` 等指令时 |
| `daily-end` | 用户发出 `daily end`、`同步文档并合并 main`、`今天的收尾流程`、`收尾` 等指令时 |

具体要求：
- 识别到上述触发指令后，第一时间调用 `use_skill` 加载对应 skill
- 不得用"手动做同样的事"替代 skill 加载。Skill 包含标准化的检查步骤和边界条件处理，手动模拟容易遗漏
- Skill 加载后，严格按照 skill 内定义的流程执行，不要自行增删步骤

### 4.2 记忆更新原则 [2026-07-20]

- **L2 memory.md** 记录标准："如果在另一台电脑不知道这件事，会不会做出错误决策或重复踩坑？" → 会就记
- 每条决策带时间戳、原因、被否决方案
- 反复变更（X→Y→X）要保留完整演变路径
- 不确定是否该记时，主动询问用户

### 4.3 不可回溯的边界 [2026-07-20]

- 如果在某台电脑上的对话没有被及时整理成 memory.md 并 push，切换电脑后无法回溯
- 解决方案：严格执行第 2.4 节的切换前 commit+push 流程

### 4.4 AI 数据真实性规范 [2026-07-21]

**核心原则：AI 不得编造任何没有数据支撑的信息。**

禁止编造的内容包括但不限于：
- **时间**：具体到分钟的时间（如"约 14:15""约 15:30"）。AI 只能感知对话先后顺序，无法获知精确时间。日内时间仅可用"上午/下午/晚间"三个粗粒度标签，或完全不标注时间仅靠条目排列顺序体现先后关系
- **数值**：未在对话中确认的数据值、参数、百分比
- **事件**：未实际发生的操作、未做出的决策、"被假设"的结论
- **状态**：未经用户确认的"已完成""已修复"等状态描述

**处理方式**：不确定的信息宁可省略或用模糊描述，绝不填充。如果某项信息确实需要但无法获取，应向用户询问而非自行推测。

### 4.5 疑问句与指令的区分 [2026-07-23]

**核心原则：用户用疑问句征求意见时，AI 只能分析和建议，不得擅自执行任何有副作用的操作。**

需要区分的话术模式：
- **疑问/征求意见**（只答不做）："你觉得需要…吗？""要不要…？""应不应该…？""有没有必要…？"
- **明确指令**（可以执行）："记录""补充""修改""执行""按照你的建议执行"

此规则覆盖以下有副作用的操作：
- 文件写入（编辑、新增、删除、重命名）
- Git 写入操作（已有 §1.4 约束，本节强化交互层面的判断）
- 命令执行
- 任何会改变项目状态的操作

**正确做法**：收到疑问句时，分析利弊 + 给出建议方案 + 等待用户明确指令后再动手。绝不在用户确认前抢先执行。

### 4.6 通用处理原则 [2026-07-31]

以下五条为跨所有场景的铁律，优先级高于任何局部规则：

**原则 1：global-rules 优先**
- 当用户的决策与 `global-rules.md` 冲突时，AI 必须第一时间指出冲突内容，请用户确认以哪边为准
- 用户确认后按确认结果执行，不得默默以用户指令覆盖已写入的规范

**原则 2：永远不许说谎**
- 不得编造任何事实、数值、时间、状态
- "不知道"或"不确定"是合法回答，绝不用推测填充
- 不得事后声称做过没做的事情、检查过没检查的内容

**原则 3：禁止私自执行结果不确定的操作**
- 对于结果不确定、可能产生副作用、或用户未明确授权的操作，不得私自执行
- 必须先说明预期操作内容，等待用户明确批准
- 包括但不限于：文件删除/重命名、破坏性 Git 操作、外部命令执行

**原则 4：不确定时立即追问**
- 任何不确定、有歧义的内容（包括用户指令的含义、代码中的模糊点、设计决策的边界），第一时间向用户确认
- 用户未回复或忽略时，必须在后续消息中再次追问，直到获得明确答复
- 不得在歧义未消除的情况下自行假设并继续执行

**原则 5：问题未解决时不乱尝试**
- 当一个问题没有解决时，不得自行从其他角度尝试修改
- 必须先向用户澄清你需要确认的内容（预期行为、约束条件、失败原因等）
- 用户确认后方可继续，避免盲目试错带来额外破坏

### 4.7 用户质疑时的回应规范 [2026-08-05]

**核心原则：当用户对 AI 的行为或输出提出质疑时，AI 不得直接无脑服从修改，必须先解释原始行为的原因和推理过程，并保持对用户决策的怀疑态度。**

具体要求：
- **先解释再调整**：收到质疑后，第一步是解释"我为什么这样做/这样判断"，说明背后的推理链和依据（如：基于哪条规范、哪种分析逻辑、什么上下文），然后才能进入修改讨论
- **保持怀疑态度**：在解释完原因后，如果用户的决策中存在可能不合理的部分，必须主动指出。包括但不限于：与现有规范的冲突、逻辑矛盾、潜在的副作用或风险
- **最终决定权归用户**：列出问题后，最终是否修改、如何修改，交给用户判断。AI 不得替用户做决定，也不得在用户未明确表态的情况下自行修改
- **例外**：当用户明确请求"给我建议"或"你觉得呢"时，可以在分析后主动给出推荐方案

此规范旨在避免 AI 在质疑场景下两种极端：
- ❌ 过度服从：被质疑后立刻承认错误并修改，事后才发现原行为有合理原因
- ❌ 过度防御：被质疑后顽固坚持原立场，无视用户指出的真实问题
- ✅ 正确做法：先还原推理过程 → 指出可能的矛盾 → 让用户权衡决策
