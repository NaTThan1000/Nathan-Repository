## 2026-08-21 (会话#14) — 升龙 jRePress 修复 + 冲刺跳/空中冲刺还原

### 今日核心改动
- **升龙"必须松开再按 J"机制修复（修复"没实现"）**：
  - 新增 `jRePress` 字段（player 初始化、charStates 初始化、状态快照导出、起跳/二段跳/落地/贴墙滑行 4 个重置点同步）。

  - 之前只清 `jHoldT` 导致"持续按住 J 到 cd 结束自动再升龙"，违背用户"必须松开再按"。
  - **关键坑**：`jRePress` 必须写进状态快照（1058 行）与 charStates/player 初始化，否则角色切换或重置后字段变 undefined → 升龙蓄力永远不累计（本次"没实现"主因之一）。
- **冲刺跳 / 空中冲刺（跳跃冲刺）相关改动全部还原**（用户指令：今天改的相关内容全部还原，升龙部分保留）：
  - 删除今天加的"空中冲刺独立判断"整段、冲刺斩的空中冲刺触发分支、Dash air 块 dashT 区分、重力块 `dashT<=0`、动画 `dashAir` 走 dash、5 处冲刺跳触发点 `dashT=0`。

### 用户反复强调的雷区（务必遵守）
- **命名绝对不能混淆**：冲刺跳 = 起跳/二段跳/墙跳时按住 L 的带加速空中移动；跳跃冲刺 = 半空重新按 L 的横向冲刺（即"空中冲刺"）。两者是独立机制，绝不合并。AI 本次多次把两者命名理解反、反复想合并，被用户严厉批评。
- **不准擅自合并两个独立机制**，不准凭空臆测，改 A 不擅自改 B，先查文档再开口。
- **文档-代码不一致必须主动列清单让用户决策**，不得擅改（本次同步时如实暂停询问，用户选"同步文档删除空中冲刺触发"+"现在同步 jRePress"）。

## 2026-08-20 (会话#14) — Zero 六个特殊动作一次性接入

### 需求背景

用户连续提出 6 个 Zero 特殊动作，均为「方向键 + 攻击键 J」组合触发，逐个接入并微调刀光大小/锚点/朝向。期间资源朝向问题反复调整（AI 读不到图，只能靠解析像素数据推断朝向，多次出错被用户纠正）。

### 动作清单与关键决策 [当前方案]

**① 升龙斩（地面 W + 按住 J ≥0.1s）**：
- 按住 W+J 先打上劈，继续按住 J 累计 6 帧（0.1s）触发升龙，取代上劈；松 J/松 W/离地则放弃
- **地面段不锁升龙次数**：地面放升龙时**不置** `shoryuAtkUsed`（保持 false），故从地面跳起到二段跳前的空中段仍可再放一次升龙，但需**松开 J 再重新按住 W+J 蓄力**（`jRePress` 标志：升龙触发后置 false，持续按住不累计蓄力，须松开重按才允许）；同一长按不连发
- **升龙不重置二段跳**：升龙跃起**不修改** `jumpCount`（修复"二段跳用完→放升龙→又能二段跳"的 bug）
- **空中段限一次**：二段跳前的空中升龙触发后置 `shoryuAtkUsed=true`，二段跳（重置点清）后可再放一次
- 80° 仰角跃起（用户确认「与水平面夹角 80°」），最大高度 = 跳跃 0.9 倍（垂直初速 -5.41 按物理公式 h=v²/2g 反推）
- 达到最高点前锁水平位移（用户确认），上升阶段禁二段跳（AI 默认决策，用户未异议）
- 刀光 `up-shoryu` **左对齐**（素材面朝左，面朝右镜像）

**② 旋风斩（地面 S + J）**：
- 用户确认伤害 3、每帧判定、斩击波速度 6.1（与子弹一致）
- 斩击波 `storm-blade2` 是**白底**（非绿底），AI 去白底生成 `storm-blade2_clean.png`（保留红色边缘浅粉抗锯齿，tol=18）
- **斩击波方向反复出错**：AI 最初用 `p.facing` 发射导致面朝左时方向反；后分析像素能量梯度（红度左→右递增）确认波前朝右，改为固定左右发射（`spawnStormWave(1,1)` / `spawnStormWave(-1,-1)`）
- **斩击波消失 bug**：碰撞盒用整图尺寸 446 高，从角色中心发射后底部穿地面立即撞墙消失；改用手写 frames.json 记录真实内容包围盒 327×189 解决
- 用户强调「右侧发射」，确认锚点 = 左边缘对齐角色（非居中）

**③ 圆月斩（空中 J）**：直接套用 air-blade，居中镜像，替代原跳跃斩击；大小经多次调整（1.5→1.8→×1.8→×0.8=3.24）；**空中 W+J 回退**：当滞空已用过且升龙也已用过（升龙仍可用时由派生块蓄力、不在此回退）→ 走圆月斩，保证空中 W+J 始终有攻击可放

**④ 滞空斩（空中 W + J）**：blast-blade → 停滞 → blast-blade2；用户先要求「停滞 10 帧」后又改为「取消停滞」（`MELEE_FLOAT_STALL` 10→0）；两部分缩放分别调整（第一部分 ×0.8、第二部分 ×1.1）

**⑤ 下劈斩（空中 S + J）**：45° 斜向下冲刺，down-blade 逆时针旋转 45°（左下）/ 135°（右下）；用户纠正「右下应该逆时针 135° 而非镜像」

**⑥ 冲刺斩（地面冲刺中 J）**：2 倍冲刺距离（`MELEE_DASH_T`=42=2×DASH_TIME）；用户先给 dash-blade（单帧白底）后改为 dash-blade2（8 帧序列帧）；顺时针旋转 90°，左方向镜像（scale 在 rotate 之前）；**仅地面冲刺中 J 触发**（空中冲刺触发已移除）

### 关键 bug 攻克

**1. 冲刺斩读成 air-blade（grounded 失效）**：
- 现象：地面冲刺中按 J 触发的是圆月斩（air-blade）而非冲刺斩
- 根因：地面冲刺期间角色 vy 保持 0（dash 不受重力），脚底贴地但碰撞检测 `overlap` 严格大于判定为 false，`grounded` 永远 false（站立时靠每帧下坠 0.24px 触发贴地才恢复 grounded）
- 修复：碰撞检测末尾对 `isDash || dashAtkT>0` 且 `hasGroundBelow()` 时补回 `grounded=true`

**2. 斩击波方向反 + 消失**（见动作②）

### 资源处理（本次新切割）

- `storm-blade2.png`（白底单帧）→ 去白底生成 `storm-blade2_clean.png` + 手写单帧 frames.json（轻量 `loadStormBlade2`）

## 2026-08-19 (会话#12) — Zero 上攻击 + 二段跳 + 怪物受击击退

### 上攻击（W+J）[当前方案]

- **触发**：Zero 地面按住 `W` + 按 `J`（`p.upAtk = p.grounded && wR`，空中按 W 无效走普通攻击），仅第 3 段向上斩
- **跃起**：角色同时向上跃起（`P.JUMP * 0.8`），且计入二段跳次数 `jumpCount = 1`——落地前仍可再接二段跳（用户确认此联动）
- **刀光**：175° 旋转（面朝右 -175° / 面朝左 +175°），区别于普通挥砍的 90° 固定
- **判定框重做**：锚点从角色前方移到头顶上方（`P.PH * 0.6` 处），垂直矩形覆盖刀光两端（原前方矩形无法覆盖上斩范围）
- **击退**：命中怪物向上弹开（power 2.5，见下）
- **决策**：上攻击定义为"第三段的强化形态"，不新增独立连击段；与二段跳次数联动（跃起消耗一次跳跃资格），但保留空中二段跳空间（jumpCount 到 1 而非 2）

### 二段跳 [当前方案]

- **触发**：空中再按 K（`jumpCount < 2`），高度 = 原跳高 × 0.8（`P.JUMP * 0.8`），重新播放起跳动画
- **墙跳不消耗**：墙跳时 `jumpCount` 保持不变，墙跳后空中仍可再二段跳
- **落地重置**：`jumpCount = 0`
- **配合上攻击**：上攻击跃起将 jumpCount 置 1（不是 2），使上攻击后仍能二段跳一次
- **决策**：用户明确要二段跳"高度低一点"（0.8 倍），并确认墙跳不消耗次数的联动设计

### 受击击退 knockEnemy [当前方案]

- **函数**：`knockEnemy(en, dirX, dirY, power)`，命中怪物时施加方向性弹开速度
- **参数约定**（用户确认的强度体系）：
  - X 子弹：1.5（水平）
  - Zero 水平挥砍：2.0（沿 `meleeDir`）
  - Zero 上攻击：2.5（向上）
- **衰减**：持续 8 帧（`knockT`），每帧速度 ×0.85
- **暂停**：击退期间怪物 AI 暂停（`ai()` 开头 `knockT > 0` 直接 return）、物理跳过（`enPhys()` 击退期间跳过重力/地面碰撞，避免击退被地形立即吃掉）

- 与网页算法一致，适合批量/脚本化生成

### 去绿幕算法演变 [当前方案]

这是本次会话攻克的核心难题，经历了三次迭代：

**v1（旧算法，有 bug）**：宽泛阈值判断 `g > r + tol && g > b + tol && g > 80`，把"偏绿的像素"都删掉。

**问题暴露**：`middle-bullet.png` 的子弹本体是白色 + **绿色描边**（`0,168,88`、`0,200,104`、`0,224,104`、`104,248,176`），背景是纯绿 `(0,255,0)`。旧算法把子弹的绿色描边也当背景删了，导致导出"像素变大、中间空白、只剩零星点"。

**v2（泛洪填充，未采用）**：从图片边缘纯绿背景 flood fill，只删连通的绿色。验证后发现问题依旧——子弹描边与背景连通，泛洪填充照样误删。

**v3（当前方案，精确删纯绿）**：只删除「贴近纯绿」的像素，判定条件改为 `g >= 255 - tol && r <= tol && b <= tol`。关键在 `r <= tol && b <= tol`：前景绿色描边如 `0,168,88` 蓝分量 88 > tol(30)，不会误删；只有纯绿背景 `0,255,0`（红 0 蓝 0）命中。验证：middle-bullet 各帧内容像素数从 117/79/48/178/176 提升到 205/190/224/348/376，纯绿残留 0。

**关键教训**：去绿幕不能假设"前景不含绿色"。当素材本身含绿色描边时，必须用精确匹配背景色（而非宽泛的"偏绿"阈值）来区分背景和前景。

### resetView 默认选区修复

原 `resetView()` 加载图片后默认选区 = 整图（`y0=0, y1=612`），导致 `getContentBBox` 扫描整个高度，每帧混入多行内容。改为：自动检测水平行后选第一行。导出时增加多行警告（选区高度 > 图高 35% 时弹窗确认）。

### 蹬墙方向强制位移 bug 修复 [当前方案]

这是本次会话攻克的核心问题，经历完整推理链：

**问题现象**：蹬墙后的 0.1s 强制位移"感觉只对冲刺蹬墙生效，普通蹬墙没生效"。

**根因定位**：
- 移动逻辑 `if (p.wjLock > 0) { p.vx = -p.onWall * P.WALL_JUMP_X; }` 每帧读取 `p.onWall`
- 但 `onWall` 在角色离墙瞬间（下一帧）即被 `wallCheck` 重算为 0
- 于是普通蹬墙的强制位移变成 `-0 * 5.5 = 0`，方向锁定立即失效

**为什么冲刺蹬墙"看起来对"（巧合而非正确）**：
- 冲刺蹬墙设置 `dashAir = true`，导致移动逻辑外层 `if (!p.isDash && !p.dashAir)` 为假，`wjLock` 分支根本不执行
- 而 `dashAir` 加速分支又有 `p.wjLock <= 0` 条件，`wjLock` 期间也不执行
- 所以冲刺蹬墙的 `vx`（蹬墙瞬间写死的 `-onWall * WALL_JUMP_X * DASH_MULT`）在 0.1s 内无人覆盖，靠"碰巧没被改"维持，方向稳定只是偶然

**修复方案**：新增 `wjDir` 字段，在蹬墙触发时保存 `p.wjDir = -p.onWall`，移动逻辑改为读 `p.wjDir` 而非 `onWall`。两条蹬墙路径（普通/冲刺）统一显式保持方向，不再依赖脆弱状态。
