- 本条汇总本聊天11月6日至8日的讨论，不代表设计已进入运行版本。当前正式版仍是11月6日新怪物单步版；本轮只设计讨论与文档同步，未修改运行代码、配置或资源。
- 房间地形、怪物阵容与初始站位作为完整战斗共同设计，先形成固定攻略目标，成熟后再考虑肉鸽随机。现有预算随机小队与随机锚点出生未被本轮替换。
- 地图探索初步采用可折返的房间网络。曾比较不可折返向前分支，助手把实体房间向前分支当第三类，用户指出本质仍不可折返；不能将其作为已采纳的第三种结构。用户希望探索资源、获得隐藏或有门槛的收益，控制空房移动与重复清理的拖沓。
- 小密室、条件密室、推箱、隐藏入口、限时方向解谜、有限步数谜题均仅讨论，未选定。用户倾向鼓励有正面收益的操作；限时输入与低操作门槛存在取舍，不限时解谜需有实际判断，不能只照提示执行。不得把固定尺寸密室、通用可推箱、箱撞怪伤害或挑战条件写成已定规则。
- 回访资源设施候选包括原地回血／剩余补给、商店、献血、交换、道具回收、重铸等；用户认为可参考，不等于逐项采纳。独立设施房为主、战斗房密室补充是助手建议，未最终确认。当前红心、蓝心、金币、炸弹和钥匙可作为补给；是否增删资源未定。拆解不新增材料的回收商仅为建议，当前被动无限叠加、重复道具不可拾取，不能假定已有大量淘汰装备。

### 局内成长目标与道具获取 [用户明确／规则草案]

- 暂不设经验升级。道具随机刷新，拾取前展示效果，玩家自行决定拾取；没有采纳普通奖励三选一、强制随机改写攻击或装备槽管理。
- 宝物房必掉道具，Boss房击杀Boss后必掉；宝箱、怪物和木箱的道具出现按配置决定，其他随机来源概率暂定较低。具体数量、掉率、配置字段与现有实现需后续任务核对，本次不修改。
- 探索目标为额外获得1～2个道具，但按每层还是整局未明确；地图阶段再分配来源。金币目前用于商店购买道具或资源，暂不扩展用途。技术奖励的具体标准和形式留待实际内容设计，不将助手建议的重抽／替换视为决定。
- 目标为六层，每层至少出现一次有分量的阶段强化，可由多个普通道具交叉组合形成；允许开局天胡或厚积薄发。阶段强化是体验目标，不能据此宣称每层随机奖励必然组成强组合。
- 单件可以主要改变战斗逻辑（包括远程变近战、优势与代价交换），强度暂不显著提升，平均清房时间／资源／难度可大致相当或微进步；不要求每种打法在每个房间表现相同。1～2件可形成阶段变化；具体道具由用户稍后提供预想稿。
- 探索为额外追求；不探索应保留高水平玩家靠深度理解通关的小概率，但挑战极大且不硬卡。探索增加强化机会与通关可能，仍需理解玩法。希望技术奖励更多选择，也允许主动高风险高收益，具体机制未定。
- 设计顺序：先确立成长获取规则，再讨论具体道具和组合；后续设计战斗房、地格、资源设施与整层网络，局外成长尚未讨论。不得为了确定成长规则提前锁定未采纳房型。

### 多维成长机制暂停与协作方法 [用户决定／技能已建立]

- 用户希望有主动制造突破、操作角色外单位或物体、消耗有限储备的体验；倾向能力主要在战斗中发挥、有限成本救险、配置管理适度，并能拓展探索互动。这些是目标，不构成主动槽、跟班或地图法术的实施决定。
- 用户指出助手反复用已举例机制替代设计推导。今后先明确新增机制的工作，再按“能改变什么／何时决定／代价是什么／与已有规则如何关联”推导能力，最后选择载体；分别判断新效果与独立系统是否有必要。数值平衡不能替代玩法成立性判断。
- 本次用户明确暂停主动道具、一次性道具、佩戴被动、跟班、地图法术等扩展维度的选择。等实际深入体验后，由用户指出期待或缺失体验，再协助判断内容调整、规则修改或新增机制。不要继续将上一轮候选当作待实施清单。
- 通用技能 game-design-reasoning v1.0.0已安装，仓库镜像位于codex-setup/game-design-reasoning；提交a192f90已推送main。方法包括目标澄清、需求发现、原因定位、具体方案比较和最小验证。方法本身可跨项目使用，项目决定不写成全局规则；本轮不更新技能或AGENTS。

### 追击方向与寻路 [用户要求＋AI具体配置／已实施]

- 用户要求横纵坐标差较大的轴优先，相同时随机选轴；同时否定“两条靠近方向都堵住就直接原地不动”，要求能自动绕路。
- 当前配置为最短可达路线优先，同长路线按长轴优先／等轴随机选首步。无遮挡时直接满足长轴原则；障碍使绕路必要时，允许先侧移或暂时远离玩家；障碍包括墙、房界和其他怪物。无法到达玩家邻格时先走向最近可达位置，已在最近位置或完全被堵住才等待。此具体组合由AI判断实施，用户尚未反馈最终试玩结果；不能描述为用户另行验收。
- 不锁死必须走长轴、不做“两轴都堵就停”的简单降级；用同长路线优先级避免原BFS固定方向顺序偏置。每次重新规划，范围和攻击条件保持现有规则；跳跃射手及Boss不套用这条步行追击算法。

### 子弹时间方向、原型验证及正式迁移 [用户确认／已实施／完整体验待验证]

- 定位调整：后续不再绑定模仿以撒或以撒式核心体验。当前核心目标是双摇杆十字射击结合半回合制，让低操作能力玩家感受射击危险与刺激，同时有充分思考时间、放心尝试，并经历多样战斗。不是已承诺新输入设备支持。
- 缘由与未采纳方向：体验者不理解回溯意义，用户认为回合制已有思考时间，回溯拖慢节奏。曾讨论一移一攻、移动或攻击二选一、不可逆MP/AP、一步或一枪，均未按最初提案直接采用。AI把现有危险预告循环当新方案，用户指出后撤回；不能把已有机制改名当成新方案。

### 挤出、碰撞与落脚效果 [最终决定]

- 早期曾试验取消所有普通碰撞伤害、角色可以穿越但不能最终共格；后续用户明确改为所有怪物均保留碰撞伤害。玩家主动移动可穿过怪物并受伤；玩家回合结束时若仍重叠，挤出玩家，不能沿用“最后一点移动不能进入怪物格”的旧限制。

### 资源掉落 none 权重 bug 修复 [当前方案]

- **[问题]** 用户测试发现摧毁大便几乎一直掉资源，清空房间也从不空掉，和配置中 `none` 的高权重（如 850/1000=85%不掉）明显不符

  2. 遍历时不过滤 `none`，正常参与权重累减；权重 ≤0 的条目 `continue` 跳过

- **[根因分析]** 两个原因叠加：①**条件死区**：`flying_eye_i` 的 `random_wander` 没指定 `range`，默认 5，导致 `dist>5` 才算 `out_of_range`；但 `shoot_fan` 的 `range:4` 要求 `dist≤4`。距离=5 时两个 action 条件都不满足→原地不动。`flying_eye_iii` 的 `random_wander`(默认range=5) 也会误匹配到距离6的情况。②**随机方向撞墙**：`random_wander` 代码只随机选一个方向然后尝试走 stepCount 步，第一步就可能撞墙/怪物/边界→path 为空→原地不动。在房间边缘/角落，25%~50%概率选到不可行方向。
- **[决策]** ①`monster-db.json` 中三个等级浮游眼的 `random_wander` 补显式 `range`，与同等级 `shoot_fan` 的 range 对齐（4/5/6），消除死区。②`calcAllMonsterPaths` 中 `random_wander` 分支增加 `validDirs` 预筛选：先 `filter` 过滤出第一步可行的方向，再从有效方向中随机选。浮游眼和蓄力魔像共享此分支，同时受益。③`shoot_fan` 的 `after_effect` 中的 `random_wander` 独立副本也同步增加 `validDirs` 过滤，多一个 fallback（无可行方向时随意选一个）。
- **[验证结果]** 与蓄力魔像 `charge_line` 已有的方向预筛选（`pickChargeDir`→`randomMovableDir`→`canMoveMin1`）模式一致：都是"filter → pick random"范式。两处差异（random_wander用4方向、charge_line用8方向含对角线）是刻意设计，不需对齐。

- **[问题]** 7/24 统一了 `movement` 结构（mode/steps/stepMode/weight），但移动方向策略和 AI 参数仍然分属两个维度——`movement.mode` 管方向、`aiType`+`aiParams` 管具体行为参数。浮游眼既需要 `movement.weight`（移动概率）又需要 `aiParams.shootRange`（射程），配置分散在两个对象中。Boss Jumper 的跳跃参数也在 `aiParams` 中，与实际的行动逻辑分离。

### Git 推送：HTTPS被封 → SSH替代方案 [当前方案]
- **[问题]** 本机网络 DPI 防火墙拦截 git/curl 对 github.com:443 的 HTTPS 连接（TCP 握手成功但 TLS SNI 被 RST），而 SSH 22 端口正常。PowerShell/.NET 的 Invoke-WebRequest 可访问 GitHub API（走不同 TLS 栈），但独立 curl.exe 同样超时
- **[诊断过程]** ①Test-NetConnection 443 True（TCP通）②git push 超时 21s ③`GIT_CURL_VERBOSE=1` 确认 curl 层 TCP 超时 ④PowerShell Invoke-WebRequest 访问 api.github.com 成功 ⑤确认 sslbackend=schannel 无代理
- **[密钥生成]** 生成 ed25519 SSH Key：`C:\Users\Fishy\.ssh\id_ed25519`（`ssh-keygen -t ed25519 -C "nathan-zhang-github"`）
- **[Deploy Key 绕行]** 用户级 SSH Key API 需要 `write:public_key` scope，但存储的 PAT（`gho_*`）只有 `gist, repo, workflow`。仓库级 Deploy Key API（`POST /repos/{owner}/{repo}/keys`）仅需 `repo` scope，成功添加（ID: 157732142，read_only=false）
- **[凭据提取]** 通过 `cmd /c "type .temp_cred.txt | git credential fill"` 从 Windows Credential Manager 提取 token（cmd pipe 避免 PowerShell 编码拦截）
- **[最终方案]** `git remote set-url origin git@github.com:NaTThan1000/Nathan-Repository.git`，SSH 22 端口稳定推送
- **[跨电脑注意]** 其他电脑的 remote 仍为 HTTPS（需同样改为 SSH，或生成新 Key 走 Deploy Key API），SSH Key 私钥仅本机持有不可迁移
