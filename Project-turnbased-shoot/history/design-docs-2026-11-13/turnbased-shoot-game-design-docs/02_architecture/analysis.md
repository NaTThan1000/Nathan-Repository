# 系统架构分析

## 问题：支撑单局循环的最小系统边界是什么？

状态：confirmed

### 广度分析

沿用顶层三组职责，能保持体验目标与架构对应；若把输入、射击、掉落、地图、商店等各自拆成设计系统，会放大接口数量；若把整局全部写成一套规则，则会混淆战斗结果、关卡推进和构筑变化的责任。

### 深度分析

建议保留三组核心系统，并明确共同的信息与表现支撑：

- 战斗拥有行动与伤害结算、怪物计划、危险应对及战斗结果；读取地图条件与已生效构筑能力。
- 关卡拥有地图、房间与楼层状态、遭遇配置、进出及推进条件，使用战斗结束结果推进流程。
- 构筑与资源拥有道具、协同、资源账户、奖励生成／领取与消费，依据关卡奖励配置和已确认结果更新玩家能力。
- 信息与表现读取上述规则状态与结果，呈现危险、动作、伤害、成长与选择。实际输入仍需规则验证；不因显示内容自行重算一套伤害或清房规则。

奖励责任区分：关卡提供奖励机会与配置，战斗提供事实结果，构筑与资源负责生成和发放实际内容。具体事件协议与掉落时点留到系统设计，不据此改动现有代码。

### 综合判断

以三组核心系统承载单局，信息与表现作为跨系统支撑。新架构为设计草案，现有源码仍有共享作用域和混合调用，未完成逐函数审计，不能称实现已符合上述边界。

### 用户确认

2026-11-10，用户认可战斗、关卡、构筑与资源三组系统的责任边界，以及信息与表现的共同支撑职责。依赖图与数据流根据这些边界整理，具体规则时点和接口留待系统设计。

## 问题：怎样保持Demo范围并支持后续扩展？

状态：confirmed

现阶段围绕单局状态、能力效果、奖励配置和结束结果设计明确边界，不提前实现局外培养、多角色扩展和通关后扩展。未来新增能力应通过明确效果与规则接口接入，不靠各处临时特判。具体接口需从真实玩法需求推导，不为未知扩展先建立完整框架。

### Demo之后的验证顺序

单局体验成立后，建议先验证最小的共享培养循环，从本局带回成长资源，经一次培养后再出发，观察它是否带来可感知的帮助与重试期待。探索差异先根据试玩反馈确定优先级，若基础探索的变化仍不足，则先解决该缺口。角色独立培养与通关后扩展保留后置。用户表示两种顺序均可，并同意按助手建议推进。因此采用共享培养优先、基础探索缺口优先修正的条件顺序。
