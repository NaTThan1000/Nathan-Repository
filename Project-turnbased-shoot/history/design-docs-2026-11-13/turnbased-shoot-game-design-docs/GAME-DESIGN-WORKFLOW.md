# 游戏设计文档分层工作流

> 用「四层递进 + 结论与推理分离 + 四道闸门」，把一个游戏点子推到可执行的系统设计。
> 模板目录：本文件夹（`Workflow/Game_Design_Template-game-design-docs/`）
> 已填示例（参考答案）：`Workflow/Game_Design_Example_Weapon_Farm_Dual_Loop-game-design-docs/`

---

## 一、这套文档解决什么问题

| 问题 | 对应机制 |
|---|---|
| 点子越想越大，收不住 | 每层都有「边界声明」和「不做清单」 |
| 越级设计，上层的假设还没定就开始写细节 | 强制自上而下，上一层 `design.md` 未定稿不进下层 |
| 只留下结论，丢失"为什么"和被否决的方案 | 每层配 `analysis.md`，三段式记录推理链 |
| 内容无限膨胀，MVP 永远做不出来 | P0 / P1 / P2 分级，后置必须写原因 |
| 文档写完没人能验收 | 每层末尾强制「验证标准」（问句形式） |

## 二、目录结构

```
{项目名}-game-design-docs/
├── README.md                        ← 快速开始 + 填写标记约定
├── GAME-DESIGN-WORKFLOW.md          ← 完整使用说明（本文件）
├── 00_concept/                      ← L1 概念设计
│   ├── design.md                    ← 定稿结论
│   └── analysis.md                  ← 推理过程
├── 01_top_design/                   ← L2 顶层设计
│   ├── design.md
│   └── analysis.md
├── 02_architecture/                 ← L3 系统架构
│   ├── design.md
│   └── analysis.md
└── 03_systems/                      ← L4 系统设计（按需复制 N 份）
    ├── S01_核心玩法/design.md + analysis.md
    ├── S02_xxx/design.md + analysis.md
    └── ...
```

> `03_systems/_TEMPLATE/` 是**空白系统骨架**，实际使用时复制并重命名为 `S01_xxx/`、`S02_xxx/`……命名规则见第七节。

## 三、四层职责

| 层 | 回答什么问题 | 主要产出 | 本层明确"不做" |
|---|---|---|---|
| **L1 `00_concept`** | 这个游戏不可替代的核心承诺是什么、给谁玩、什么基调 | 一句话概念、核心幻想、目标用户、玩家身份、体验目标、情绪基调、不是什么 | 战斗时长、内容数量、资源流、系统清单、MVP 全部留给 L2 |
| **L2 `01_top_design`** | 循环单位是什么、局外段/局内段各是什么、规模多大、长期结构 | 顶层定位、规模锚点、核心循环图、流程表、系统范围表、不做清单 | 不写具体内容表（作物/敌人/设施清单）、不写数值 |
| **L3 `02_architecture`** | 支撑这个循环需要哪些系统、谁依赖谁、哪些是 P0 | P0 系统清单、P1/P2 边界、系统依赖图、数据流图、MVP 最小闭环 | 不展开单系统内部规则 |
| **L4 `03_systems`** | 每个系统内部：范围、关键操作、最小闭环、后置项 | 设计目的、系统范围、核心循环、P0 最小闭环、P1/P2 后置、验证标准 | 不定义数值、内容表、UI 布局 |

**铁律：上一层 `design.md` 没定稿，不进下一层。** 每层的"边界声明"都在说"XX 留到下一层决定"，越级写必然产生前后矛盾。

## 四、两个文件的分工

| 文件 | 内容 | 回答 |
|---|---|---|
| `design.md` | 定稿结论：定位、结构图、范围表、规则边界、P0/P1/P2、验证标准 | "最终是什么" |
| `analysis.md` | 2~3 个真正的岔路口问题，每个按 **广度分析 → 深度分析 → 综合判断** 展开 | "为什么是这样、否决了什么" |

### 状态字段约定

`analysis.md` 中每个问题条目下必须带一行状态：

| 状态值 | 含义 | 何时使用 |
|---|---|---|
| `agent_proposal` | AI 提案，待用户确认 | AI 产出结论后立即标记 |
| `confirmed` | 用户已确认，结论已提升进 `design.md` | 用户明确拍板后 |
| `deprecated` | 该方案已废弃，但**保留原文**供回溯 | 结论被后续方案取代时 |

**状态流转：** `agent_proposal` → `confirmed` / `deprecated`。
**禁止：** 直接删除已废弃条目。演变路径（A→B→A）必须完整保留，在旧条目顶部注明「[已废弃] 被 XX 取代」。

### 写作要点

- 「广度分析」列 3~5 个可选方向，**每个都写出它的代价**，不要只夸。
- 「深度分析」说明为什么剩下的方向成立/不成立，点出真正的机制因果。
- 「综合判断」给出**唯一**结论句，可直接提升进 `design.md`。
- 被否决的方案和否决理由必须留在正文里——这是 `analysis.md` 信息量最大的部分。

## 五、填写顺序（SOP）

**Step 0｜创建项目文档集**
复制 `Game_Design_Template-game-design-docs/`，重命名为 `{项目名}-game-design-docs/`。
保留四层目录名，删掉 `_TEMPLATE` 之外你不需要的系统目录，其余留空。

**Step 1｜L1 概念设计**（先写 `analysis.md`，再写 `design.md`）
写两个问题：① 什么是这个游戏不可替代的核心承诺？② 怎样防止内容扩张稀释核心幻想？
结论提升进 `design.md` 后，`design.md` 顶部写 `最后定稿: YYYY-MM-DD`。

**Step 2｜L2 顶层设计**
先补三张图（核心循环 / 完整循环 / 资源流）→ 再补「循环单位流程表」→ 再补「系统范围表」→ 最后写「不做清单」和「验证标准」，收在「当前结论」。

**Step 3｜L3 系统架构**
从 L2 的「系统范围表」逐行推导，产出「P0 系统清单」（每个系统必须有 目的 / 输入 / 输出 / P0 原因 四栏）→ 画「系统依赖图」和「数据流图」→ 写「MVP 最小闭环」→ 写「风险与校验」。

> 检查点：L3 的 P0 系统数量应与 L2 系统范围表基本对齐；多出来的系统要么砍掉，要么回 L2 补进范围表。

**Step 4｜L4 系统设计**
按 L3 的 P0 系统清单，逐个把 `_TEMPLATE/` 复制为 `S0N_系统名/`，每个系统写：范围（负责/不负责）→ 核心循环 → 关键操作或结构 → 接口输出 → P0 最小闭环 → P1/P2 后置 → 验证标准。

**Step 5｜回填校验**
- L4 中任何"需要上层解释"的内容，回填到 L3/L2。
- 每层末尾的「验证标准」逐条自问能否回答。
- 无法归入 P0 又给不出后置原因的功能，直接砍。

## 六、四道闸门（每层结尾必过）

1. **边界声明** —— 明写"本层不负责什么，留给谁"。没有它，文档会一路膨胀。
2. **不做清单 / 不是什么** —— 表格形式，**每条必须写原因**。后续新点子撞上这张表就能当场否决。
3. **P0 / P1 / P2 分级** —— 后置项**必须写后置原因**（"需要先验证 X"），不能只写"以后再说"。
4. **验证标准** —— 用可回答的**问句**写（"玩家是否会……？"），不用"体验良好"这类无法验收的话。

---

## 七、系统目录怎么拆

**按玩家因果链拆，不按资源类型或操作拆。**
因果链 = 玩家每一步行动导致什么结果。示例：农场准备 → 出战投入 → 路线战斗 → 日结回流 → 跨天成长，因此拆成 核心玩法 / 路线战斗 / 长期成长 三个系统。

- 命名：`S01_核心玩法`、`S02_路线战斗`、`S03_长期成长`（数字保证排序稳定）。
- 系统数量：MVP 一般 3~5 个。超过 5 个通常意味着拆得太碎，接口成本会失控。
- 每个系统必须写清「输入 / 输出」和「谁负责 / 谁不负责」。同一个结论**只能由一个系统拥有**，其他系统读取。

## 八、与 AI 协作姿势

| 你说 | AI 做 |
|---|---|
| "开始设计新游戏《XXX》" | 复制模板 → 从 L1 起草 `analysis.md` 两个问题 + `design.md` 骨架 |
| "这个方向不对，改成……" | 旧条目标 `deprecated` 保留原文，新增 `agent_proposal` 条目，重写 `design.md` |
| "确认，定稿" | 状态改 `confirmed`，结论提升进 `design.md`，更新顶部日期 |
| "进下一层" | 校验上一层四道闸门是否齐全，然后起草下一层 |
| "L3 说需要一个新的 XX 系统" | 回填 L2 系统范围表 → 在 L3 清单加行 → 在 L4 复制 `_TEMPLATE` 建目录 |
| "检查一下文档一致性" | 逐层比对：边界是否越界、系统清单是否对齐、P0 闭环是否覆盖全部系统 |

**AI 硬性约束**：不得在未确认时把 `agent_proposal` 改成 `confirmed`；不得删除 `deprecated` 条目；不得越层定义（L2 里不写系统内部规则，L4 里不写数值表）。

---

## 九、维护规则

1. **结论变更双写**：改 `design.md` 的同时，必须在 `analysis.md` 追加新条目（`agent_proposal`）并把旧条目改 `deprecated`。
2. **排序**：`analysis.md` 内条目按时间**由新到旧**，新条目插在最上面。
3. **日期**：每次 `design.md` 定稿，更新顶部的 `最后定稿: YYYY-MM-DD`。
4. **只增不删**：已废弃的方案保留原文，标注取代关系。
5. **示例文件夹只读**：`Game_Design_Example_...` 只作参考答案，不要在它里面改内容。
6. 本说明与实际模板结构不一致时，以本说明为准并同步修正模板。

## 十、速查卡

| 操作 | 位置 |
|---|---|
| 新建项目文档集 | 复制 `Game_Design_Template-game-design-docs/` 并重命名 |
| 提出一个方案 | `analysis.md` 新增条目 + 状态 `agent_proposal` |
| 拍板确认 | 状态改 `confirmed` + 结论写进 `design.md` |
| 否决一个方案 | 状态改 `deprecated` + 保留原文 + 注明被谁取代 |
| 新增一个系统 | 复制 `03_systems/_TEMPLATE/` → `S0N_系统名/` → 回填 L2/L3 |
| 验收一层 | 过四道闸门：边界 / 不做清单 / P0-P1-P2 / 验证标准 |
| 判断该不该做某功能 | 它能否强化核心因果链？能否说清它改变了玩家的哪个决策？ |
