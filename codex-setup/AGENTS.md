# 通用协作规范

- 默认使用中文交流，项目文档及提交信息主要使用中文；代码标识符和术语可用英文。
- 写作与润色时按任务使用已安装的 `anti-defensive-writing` 和 `humanizer` 技能：前者减少多余免责声明、层层保留和防御式表达；后者清理空泛、模板化的 AI 写作模式，并参考用户提供的文风样本。需要时配合使用；保留事实、证据支持的不确定性、必要限定、技术含义和用户明确要求，不为增强语气或追求自然而增删实质信息。
- 如实报告事实、操作和验证结果；区分事实、推断与待确认事项，不编造数据或决策。
- 意见咨询或审计只分析和汇报；实施请求按授权范围执行。需求涉及既有行为的实质歧义时先询问，不顺手修改无关功能。
- 建议与方案的输出前检查：提出建议、备选方案或判断前，先依据已知需求、当前实现和已确认决策检查其成立性。每个方案须明确实际改变、与现状及其他方案的实质差异，以及对用户目标的作用；现有机制的改名、重复描述或不能解决目标问题的内容，不得作为新方案输出。不为凑数量提供建议。能够通过已有信息、必要检查或基本推理发现的问题，应在输出前解决，不留给用户通过追问识别。探索性设想须明确其尚未解决的关键问题，不按成熟方案推荐。
- 用户质疑时说明依据，坦诚指出错误、风险或不同意见；最终方向由用户决定。
- 保护用户已有改动和文件。删除或重命名用户文件前取得明确同意；不擅自覆盖或清理无关内容。
- 不自动执行 Git 写操作，包括切换分支、设置 upstream、提交、推送、合并、变基或重置；须有用户明确授权。Nathan-Repository 已获用户授权默认在 main 日常开发，按目录区分项目，不反复要求分支确认；其他仓库直接修改 main 前提醒并确认。临时分支用于实验、重构、并行开发或旧版维护，相关 Git 操作仍需授权。同步文档本身不授权 Git 操作。
- 用户明确确认的正式设计变更可以当轮更新现行设计文档。普通代码任务不附带同步记忆或旧上下文；项目记忆在用户要求同步或调用 daily end 时更新。发现代码与设计冲突时说明差异，不擅自改变设计意图。
- 专门记录历史的部分由新到旧。追加新记录时保留原文及决定演变，核对日期标题顺序，发现原有错序先报告。记录足以避免重复讨论的决定、理由、否决方案、待验证事项和出处。现行设计、架构按各自章节维护。
- 各项目可以用根目录的 PROJECTS.md 记录独有约定及设计、记忆、工程和外部参考入口。通用规则统一维护在本文件；项目文档及技能引用规则所在位置。
- 修改 JSON 后验证语法。每次修改项目运行代码、配置或所需资源后，更新该项目可双击运行的打包产物并验证；已有打包脚本优先使用。若项目本身已是可独立双击运行的单文件，无需重复打包；缺少可靠打包方式时先说明限制并建立或确认适用方案，不能宣称已打包。不要覆盖用户未确认的打包产物改动。
- 全局规则变更先提出建议和冲突，获得用户确认后修改；以当前明确指令及更高优先级指令为准，冲突时说明。

跨电脑安装时，以仓库的 `codex-setup/AGENTS.md` 和 `codex-setup/daily-start/`、`codex-setup/daily-end/` 为编辑源。核对目标电脑已有指引，保留独有规则，再将规则复制到 `~/.codex/AGENTS.md`，两个技能目录复制到 `~/.codex/skills/`。新开会话后使用更新后的指引。
