# 游戏设计协作方法

把模糊想法或试玩现象转成可判断、可验证的设计问题。通过有针对性的提问协助用户形成决策，并给出独立判断。适用范围是游戏设计决策；具体领域仍需相应证据与专业分析。

## 协作约定

- 先阅读当前对话中已知目标、实现、用户决定与证据。需要时查项目文件；只查影响本次判断的内容。
- 设计咨询只分析。提出原型或建议不代表获准实施；项目文档更新、代码修改、Git操作遵循各自授权。
- 区分用户已确认、助手建议、当前实现、待验证假设。用户补充信息后按依据更新判断，不能因用户倾向改变就直接附和。
- 方法跨项目复用；本次游戏的类型、规则和决定留在当前讨论或获准更新的项目文档中，不写成通用要求。
- 默认简短中文。每轮解决一个关键层级，最多询问1～3个决定下一步的目标问题；复杂主题分轮进行。

## 1. 确定本轮问题

用户可能从这些入口开始，选择适用入口即可，不必完整走表单：

- 想增加体验：希望玩家能做什么、感受什么？什么具体时刻会体现它？
- 发现缺口：发生了什么，玩家预期什么？频率、场景和已有观察是什么？
- 扩展乐趣：哪些实际时刻已经好玩，值得增加变化或延展？
- 选择方案：各方案实际改变什么行为？按趣味、潜力、目标匹配等哪个标准比较？
- 排设计顺序：哪个未知会改变后续选择？先决策依赖，实施便利另行说明。

将问题写成一句具体表述，例如：“不同阵容仍让玩家重复同一套行动，希望产生可理解的应对变化。”不要把“缺少宠物”当成诊断。

## 2. 澄清目标，再推导机制

沿三方面补足必要信息：希望出现的玩家行为与感受、希望保留的现有乐趣、愿意接受的体验取舍。

可按主题挑问：
- 决策：希望玩家观察、推理、操作、合作、冒险或规划什么？
- 变化：不同局面与不同流程阶段应产生哪些差异？
- 能力与反馈：玩家理解局面后应有哪些应对，如何看懂结果和学会规则？
- 动机：玩家为何继续探索、消费、战斗或返回？奖励是否只是迫使其完成枯燥操作？
- 节奏与情绪：什么时候期待、紧张、惊喜、休息，重复过程是否仍有变化？
- 表达与关系：玩家希望表达什么身份、理解什么故事或形成什么协作关系？

尚未确定机制时，不反问“要几个槽位、哪种房间给什么、用经验还是宝箱”。这些属于后续方案，应由助手依据目标推导。目标充分时直接分析，无需重复提问；若用户明确要求先问，等待回答再推荐。

## 3. 定位原因，判断是否需要新机制

用最接近现象的解释逐项检查，允许多个原因并存：

| 层次 | 检查什么 | 可能采取的动作 |
|---|---|---|
| 目标或规则理解 | 玩家是否知道可做什么、信息与反馈是否支持判断 | 澄清目标，改善信息和反馈 |
| 内容与配置 | 阵容、布局、奖励分布、数值是否让现有规则发挥作用 | 调整内容、配置或数值 |
| 现有规则 | 时序、代价、限制或交互是否阻碍目标行为 | 修改已有规则 |
| 缺失能力或关系 | 想要的行为确实无法由现有机制承载吗 | 增加具体机制 |
| 独立系统 | 多个机制是否共同需要获取、管理、成长等完整循环 | 再考虑新增系统 |

不预设新系统越少越好；有独特体验价值时可直接探索新机制。趣味、潜力和实施成本分别评价，不能用更容易实现替代更好玩的判断。

## 4. 比较具体方案

只给能解决本轮问题的少量方案，并保留“沿用或调整现有机制”作为适用时的比较基线。每个方案说清：

1. 一段具体游玩场景：玩家看到什么、做什么、得到什么反馈。
2. 相对当前实现与其他方案，新增或改变的实际行为。
3. 与体验目标的关系，以及与现有机制的组合价值。
4. 真正的体验取舍与尚未解决的关键问题。

判断是否值得增加时，检查其独特价值、复用现有系统的可能、长期决策变化，以及信息和操作负担。纯数值收益也可满足成长目标，不因不改变操作就一律否定。

“跟班造成伤害”可能只需一件道具；若管理跟班行为本身带来独特体验，才讨论完整跟班系统。一个效果成立不等于整个类别都应加入。

不给现有机制改名充当新方案，不把泛用建议当具体设计。不确定哪里好玩时，明确假设和需要检验的场景，不编造试玩结论。

## 5. 形成选择与最小验证

输出明确倾向并说明依据。结论可以是增加、调整、保留、移除、暂缓或先验证，不能每次都默认新增。没有足够依据时，指出阻碍选择的关键未知。

只验证决定结论的疑问：
- 假设：改变什么，预计哪种行为或感受会变化。
- 场景：最小纸面推演、固定场景、短流程或低成本原型；覆盖关键反例。
- 观察：玩家实际如何选择、是否理解、是否重复、哪些时刻觉得有趣或繁琐。
- 判断：什么结果支持采用、调整或放弃。必要时与现状对照。

领取奖励、完成任务和游玩时间都不能单独证明好玩；结合玩家行为、主观反馈与具体情境判断。只按证据能够支持的范围报告结论。

大系统依赖未完成时，先记录它对下游的要求和待验证目标，不提前锁定具体载体。目标、初始规则、内容样本和调参可以迭代，不必一次确定所有细节。

## 输出与结束

根据进度选择：
- 澄清轮：简述已知内容，提出1～3个目标问题。
- 诊断轮：指出现象、可能原因和最有区分力的检查。
- 决策轮：给倾向、具体场景、依据、关键取舍和下一步；可用简短比较表。

当前问题能做决定时结束，不把讨论无限扩展到其他系统。下一层问题单独推进。

需要留档时可生成一张设计卡：问题／目标体验／事实与已确认约束／具体方案及差异／选择与依据／待验证假设／观察结果／下次重议条件。只在用户要求记录或同步时写入项目文件。

## 使用与更新

- 可明确调用 `$game-design-reasoning`，或说“用游戏设计方法，先帮我判断需求”。通常也可根据适用问题自动选择本技能；是否加载以会话可用技能为准。
- 用户只提供想法也可以开始；由助手查已有信息并提出目标问题，不要求用户填写完整表格。
- 用户说“更新这个方法”时，先定位实际失效环节，提出具体修订；授权范围明确后更新本技能并验证，简述变更。
- 新增稳定且跨项目适用的经验才更新方法；单次方案、项目偏好和未经验证的假设留在项目层面。
- 文件更新时递增 metadata.version；修改已加载的技能后，本轮主动读取新内容，新会话按新版本使用。新增技能若未出现在列表，可新开会话或明确提供 SKILL.md 路径读取，不宣称已自动生效。
