# 系统架构分析

## 问题：支撑闭环的最小系统边界是什么？

状态：agent_proposal

### 广度分析

> 填写要点：至少比较"大系统一把梭 / 按操作拆碎 / 按因果链拆"三种拆法的代价。

- 把【A/B/C】写成一个大系统，初期简单，但责任和状态很快混杂。
- 按每种资源或操作拆小系统，边界清楚，却会产生过多接口和文档负担。
- 按玩家因果链拆分，可以让每个系统拥有明确输入、输出和失败责任。

### 深度分析

> 填写要点：逐一点出"关键责任分别由谁承担"，并强调"同一结论不能被多处维护"。

闭环中的关键责任是：【日程/节奏】触发推进；【生产系统】产出可投入资源；【投入系统】记录配置和消耗；【战斗系统】只输出过程结果；【结算系统】统一处理收益与损耗；【长期系统】处理解锁。

信息系统应读取这些系统的状态，不替代它们做规则判断。【系统 A】不直接发放【长期成长】，【系统 B】不定义【战斗规则】，这些边界能避免同一结论被多处维护。

### 综合判断

保留【系统 1】～【系统 N】共 N 项职责；实现时可组合服务，但**数据所有权和因果顺序必须保持独立**。

## 问题：怎样在 MVP 阶段保持结构收敛，同时为后续扩展留口子？

状态：agent_proposal

### 广度分析

> 填写要点：比较"现在就把扩展形态做出来"和"只留接口"的代价。

- 直接做【完整形态】能展示扩展性，但会在核心闭环验证前放大内容成本。
- 只做【最小形态】容易验证，但若不留接口，后续扩展要重构。
- 保存【状态槽位/接口】而不实现【内容】，能同时满足两者。

### 深度分析

【扩展形态】依赖【最小形态】是否成立。架构只需保存【状态字段/接口】，不必提前实现【内容结构】。

### 综合判断

MVP 使用【最小结构】和有限状态信息验证闭环；通过稳定的【结果/检查点/解锁接口】预留扩展能力，但不让未来结构进入当前核心范围。
