# 游戏开发流程

以可验收成果推进。每个项目用一份 `project-plan.json` 记录阶段、父子任务、依赖和验收。按可投入的时间随时开始或暂停，在任务里保留状态和进展。阶段通过、退回和整体复核结论在对话中确认，再同步到项目计划。

| 阶段 | 主要工作 | 阶段验收 |
|---|---|---|
| A 定方向 | 立项、脑暴、比较方案、确定验证范围 | 确认玩家体验、项目规模和首个验证问题 |
| B 试核心玩法 | 做最小可玩原型、内部自查、对照试玩 | 有可玩的证据，能决定保留、调整或换掉核心玩法 |
| C 试完整循环 | 确定范围和前置设计、做代表样段、打通目标循环、集中试玩 | 目标循环能走完，体验获认可，代表内容的制作方法和成本支持扩大投入 |
| D 正式制作 | 按成果批次实现、制作、整合和验收 | 约定功能和内容已接入，完整目标流程可玩 |
| E 测试、交付与维护 | 整体回归、调优、验收交付包、发布或内部交付、复盘 | 在目标环境验收实际交付包，确认遗留问题和后续维护范围 |

短项目可以用同一构建提供多个阶段的证据，逐阶段确认适用的验收结论。阶段收尾时查看剩余事项，确认成果达到阶段目标。

## 拆分和执行

- 父任务用一个可验收成果命名。当前和即将开工的工作拆细，远期先列成果。任务日常填写名称、具体内容、类型、优先级和状态。具体内容可记录交付物、真实依赖、进展及验收结果。明确后置或待确认的事项保留在计划里。
- 设计按「核对现状和已有决定 → 明确目标 → 比较做法 → 用户确认 → 更新 GDD」走。代码按「确认规则 → 实现 → 自审 → 构建与回归 → 实际入口验证」走。
- 关卡与数值按「确定内容作用 → 代表样本 → 固定条件对照 → 连续流程验证 → 扩量」走。美术与音效按「用途和规格 → 样件 → 场景自审 → 用户审阅 → 返修或采用 → 接入复验」走。试玩按「选构建和场景 → 记录行为与结果 → 判断并安排复验」走。
- 新需求先向你同步目标、挂靠位置、任务拆分、依赖和影响。确认纳入后写进计划。GDD 保存现行设计，Memory 保存有追溯价值的决定和理由，任务记录进度与证据链接。

## 如何选下一项

从任意阶段选择要讨论或推进的任务。概况显示当前阶段、核心体验和该阶段的进度数字。阶段卡随任务状态更新。任务按优先级和编号排列，列表显示具体内容的首句，点开查看完整内容和相关资料。任务做到一半可以在具体内容里记录进展。阶段顺序用于整体评审，实际依赖用于说明风险及回溯影响。

## 发现问题与退回

1. 先定位最早需要重做的任务，说明影响和复验方式。任务的每个版本都是独立条目。创建 v2 时写清原因、范围和本次验收条件，保留 v1 原记录。
2. 重做父任务时复制整棵当前子树。AI 提出可复用子任务及证据，由你在创建前核对。确认复用的新子任务自动标为已验收并指回旧成果，其余走正常制作和验收。前置关系随新版重接。
3. 退回较早阶段由你确认。后续已走到的阶段标为待复核，按原顺序复核。已有成果若仍有效，记录复核依据。需要重做或重新交付时创建新任务版本。旧任务记录及原阶段验收保留。

## 美术任务审阅

在工作台的美术任务详情登记候选，选择项目里的图片、音频或视频，并填写项目内路径。审阅意见绑定候选版本及文件 SHA-256。返修登记新候选，保留旧素材和意见。采用后检查实际构建的接入效果，再填写任务验收。素材文件由项目保管，浏览器授权用于页内预览，计划保存审核记录。浏览器权限失效时可重新选对应版本；内容与登记哈希须一致。

## 项目接入与维护

已有项目先用 GDD、Memory、可运行构建和实际验收记录整理任务树。无法核实的状态标为待复核。首次录入的顺序和当前阶段可作为建议，验收只记录实际结果。支持文件读写的 AI 按项目 `PROJECTS.md` 查入口；项目计划与工作台使用同一 JSON。

双击 `Workflow/Project-Workbench/workbench.html`，选择项目目录里的 `project-plan.json`。Chrome 或 Edge 可授权直接保存到原文件，其他浏览器可以打开文件快照查看。再次打开时可恢复上次读取的项目，若需要重新授权会提示。计划或工作台在外部更新后点「重新读取文件」。为已有项目生成空计划可在仓库根运行 `node Workflow/Project-Workbench/server.cjs --init <项目目录>`。

AI 直接修改计划前重新读取当前文件，保留已有结果及变更记录，写后运行 `node Workflow/Project-Workbench/server.cjs --check <项目目录>`。推荐和状态计算以工作台的 `plan.js` 为准。
